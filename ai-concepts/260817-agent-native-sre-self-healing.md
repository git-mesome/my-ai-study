# Agent-Native SRE / Self-Healing

> 채용 공고에서 발견한 용어, 2026-08-17

## 정의

시스템 장애를 감지 → 원인 진단 → 조치까지 **LLM 에이전트가 스스로 수행**하게 만드는 SRE(Site Reliability Engineering) 접근. 기존 규칙 기반 Self-Healing의 한계(미리 정의된 장애만 대응 가능)를, 에이전트의 추론 능력으로 확장한 것.

## 먼저 짚을 두 개념

**SRE(Site Reliability Engineering)**: 서비스 안정성을 엔지니어링 문제로 다루는 방법론. 모니터링/알림, 장애 대응(온콜), 원인 분석(포스트모템), 반복 작업 자동화, 에러 버짓(안정성과 배포 속도의 균형 기준) 등을 다룸.

**Self-Healing(자가 치유)**: 장애 시 사람 개입 없이 시스템이 스스로 복구. AI와 무관하게 이미 존재하던 개념 — 헬스체크 실패 시 자동 재시작(K8s liveness probe), 트래픽 몰리면 오토스케일링, 회로 차단기(Circuit Breaker)로 장애 전파 차단 등. 전부 **규칙 기반(rule-based)**: "이 조건이면 이 액션"이 미리 정의됨.

## Agent-Native SRE = 여기에 LLM 에이전트를 얹은 것

규칙 기반 자동화는 **미리 예상한 장애**만 대응 가능. 실제 장애는 원인이 매번 새롭고 복합적이라, 사람이 로그/메트릭을 뒤지며 추론하던 부분을 에이전트가 대신함.

1. **감지**: 메트릭/로그/알림을 에이전트가 실시간 관찰
2. **진단(Root Cause Analysis)**: 로그·배포 이력·설정 변경 이력을 스스로 탐색해 원인 추론 (사람이 하던 [계층별 트러블슈팅](../cs-study/network/260816-네트워크-기초-면접정리.md)을 에이전트가 수행하는 셈)
3. **조치**: 툴 호출로 직접 실행 (pod 재시작, 이전 버전 롤백, 스케일 조정, 트래픽 차단)
4. **에스컬레이션**: 확신 없거나 리스크 큰 조치는 사람 승인 후 실행 (Human-in-the-loop)

## 기존 Self-Healing과 차이

| | 규칙 기반 Self-Healing | Agent-Native SRE |
|---|---|---|
| 대응 범위 | 미리 정의된 조건만 | 처음 보는 장애도 추론해서 대응 |
| 판단 방식 | if-then 룰 | LLM이 로그/메트릭 해석해서 원인 추론 |
| 확장성 | 룰 늘어날수록 유지보수 부담 ↑ | 새 상황에도 일반화 가능 (단, 신뢰성 검증 필요) |

## 핵심 리스크

AI가 잘못 진단하고 잘못된 조치(멀쩡한 서비스 재시작, 정상 트래픽 차단)를 자동 실행하면 오히려 장애를 키움. 그래서 **조치 실행 전 사람 승인 단계**를 어디에 둘지가 설계의 핵심 쟁점 — [루프 엔지니어링](./260807-루프엔지니어링.md)의 "사람 개입 지점(human-in-the-loop)"과 같은 문제의식.

## 왜 지금 주목받는가

LLM이 **도구 호출(Tool Use)** + **긴 컨텍스트로 로그를 읽고 추론**하는 게 가능해지면서, 사람이 로그 뒤지며 판단하던 일을 에이전트가 흉내낼 수 있게 됨. 해외엔 Cleric, Resolve AI 같은 "AI SRE" 스타트업이 등장 중이고, 국내 대기업도 AIOps 방향 투자 중.
