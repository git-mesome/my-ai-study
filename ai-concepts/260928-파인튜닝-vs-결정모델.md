# 파인튜닝 vs 결정 모델(Ollaya) — 기밀 문서 등급 분류 설계 판단

> 2026-09-28 학습. 사내 N2SF 보안등급 분류 AI 설계안(KLUE RoBERTa 파인튜닝 기반)을 Ollaya 같은 결정 모델로 바꿀지 검토하고, **설계안을 유지하기로 결정**했다.

## 1. 파인튜닝(Fine-tuning)이란

- **정의**: 대량 데이터로 사전학습된 모델의 가중치를 가져와, 내가 가진 소량의 태스크 데이터로 추가 학습시켜 원하는 태스크·스타일에 맞게 조정하는 것. 처음부터 사전학습하지 않는다.
- **언제 쓰나**: 프롬프트로 기준을 설명해도 잡히지 않는 암묵적 판단 기준이 많을 때, 처리량이 많아 매번 긴 프롬프트를 넣기 비쌀 때, 같은 오분류가 반복될 때.
- **실무 순서**: 프롬프트(제로샷·few-shot)로 먼저 돌려보고 → 오분류 패턴을 분석하고 → 그래도 안 잡히면 파인튜닝한다. 파인튜닝이 첫 단계일 필요는 없다.

### 분류 태스크에서의 두 갈래

| 방식 | 예시 모델 | 특징 |
|------|-----------|------|
| 인코더 + 분류 헤드, 전체 파인튜닝 | KLUE RoBERTa, BERT 계열 | 가볍고 빠름. 고정된 등급 예측에 적합. 근거 문장은 생성하지 않음 |
| 생성형 LLM + LoRA/QLoRA | Qwen3-8B, Llama 계열 | 긴 문맥, 등급과 근거를 구조화해 출력 가능. GPU 비용·지연이 큼 |

- **LoRA**: 기본 모델 가중치는 동결하고, 일부 레이어에 작은 저랭크 행렬(어댑터)만 끼워 학습한다.
- **QLoRA**: 기본 모델을 4bit로 적재해 메모리를 더 줄인 LoRA.

### 코드에서 "파인튜닝이 일어나는 곳"

```python
model = AutoModelForCausalLM.from_pretrained(model_name)   # 사전학습 모델 불러오기 (여기까지는 파인튜닝 아님)
model = get_peft_model(model, LoraConfig(r=16, target_modules=["q_proj", "v_proj"]))  # 학습할 어댑터 부착
trainer = SFTTrainer(model=model, train_dataset=train_dataset, tokenizer=tokenizer)
trainer.train()   # 우리 데이터로 어댑터 가중치를 업데이트 = 파인튜닝
```

## 2. 결정 모델(Decision Model) — Ollaya

- **정의**: 로컬에서 오픈 웨이트 "결정 모델"(winnow, laya, kev 등)을 실행하는 오픈소스 CLI 도구(Apache-2.0). 텍스트·JSON을 입력(state)으로 받아 **타입이 지정된 질문**에 답한다.
- **특징**: 토큰 단위 생성 없이 한 번의 추론으로 답해 밀리초 단위로 빠르다. 로컬 실행이라 데이터가 외부로 나가지 않는다.
- **질문 타입 3종**: `choice`(선택지 2~255개), `score`(단계 2~10개), `noul`(참/거짓. 문서 표기 그대로)

```bash
ollaya pull laya
cat document.txt | ollaya run laya --questions grade-questions.json --format json
ollaya serve   # 127.0.0.1:11435, POST /api/decide
```

### 한계 (공식 문서 확인 기준)

- **사용자 데이터로 학습·파인튜닝 불가.** Modelfile로 정할 수 있는 것은 기본 모델, 질문 프리셋, 캘리브레이션(라벨 데이터로 온도값 재조정), 정밀도, 메타데이터뿐이다.
- **한국어 지원 여부 불명.** 문서에 보이는 언어 태그는 `laya:en`뿐이다.
- **최대 입력 길이 명시 없음.**
- 설치(`curl | sh`)와 모델 `pull`이 인터넷 연결을 전제한다.

즉 결정 모델은 "기준을 글로 설명해서 판단시키는" 제로샷 방식이고, 파인튜닝을 대체하지 않는다.

## 3. 업무 적용 — N2SF 등급 분류 설계안 판단

**설계안 요약**: KLUE RoBERTa에 C/S/O 3등급 분류 헤드를 붙여 전체 파인튜닝하고, 기관 정책 규칙 계층과 결합한다. 학습 서버와 판단 서버를 분리하고, Qwen3-8B QLoRA는 선택적 비교 실험으로 둔다. 온프레미스가 전제다.

**결정: 설계안을 유지한다.** 근거는 다음과 같다.

1. 설계안의 전제는 "가이드라인을 읽히는 것과 실제 기관 문서를 분류하도록 학습시키는 것은 별도의 작업"이다. Ollaya는 앞쪽만 할 수 있다.
2. 입력이 한국어 공문서인데, 한국어 지원을 확인할 수 없다.
3. 설계에 필요한 근거 구간, 긴 문서 청크 집계, 모델·정책·전처리 버전 묶음을 제공하지 않는다.
4. N2SF 폐쇄망 환경에서는 인터넷 기반 설치와 신생 프로젝트의 공급망 보안 검토 부담이 크다.

**참고로 남길 것**: 쓴다면 자리는 "파인튜닝 없는 비교 기준선"(TF-IDF 기준선과 같은 층위)이다. 라벨 기반 확률 보정 기능은 설계안의 `score_status: not_calibrated` 부분과 비교해볼 가치가 있다. 어느 경우든 라벨링된 평가셋이 먼저 있어야 판단할 수 있다.

## 4. 배운 점

- 새 도구를 볼 때는 "무엇을 해주는가"보다 **"우리 데이터로 학습할 수 있는가, 우리 언어·환경에서 돌아가는가"**를 먼저 확인한다.
- 제로샷·결정 모델·파인튜닝은 경쟁 관계가 아니라 **기준선 → 개선** 순서로 비교할 후보다.
- 어떤 방식을 고르든 출발점은 **검수된 평가셋**이다.
