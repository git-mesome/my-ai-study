# 비대칭 라우팅과 Stateful 방화벽

> 보안 회사 수습 기간 — 사내 문서 위키 온보딩 자료 학습, 2026-09-15

## 비대칭 라우팅(Asymmetric Routing)이란

가는 경로와 돌아오는 경로가 서로 다른 장비를 지나는 상황. 라우팅 관점에서만 보면 그 자체로 문제는 아님.

**왜 치명적이 되나**: 경로 중간에 **Stateful 방화벽**이 있으면 문제가 됨. Stateful 방화벽은 나가는 패킷을 세션 테이블(conntrack)에 기록하고, 돌아오는 패킷을 그 세션과 매칭해 허용하는 방식인데, return 트래픽이 **다른** 방화벽으로 들어오면 그 장비엔 세션 기록이 없어서 차단됨.

- 전형적 증상: **"나가긴 하는데 응답이 안 온다"**

## 원인 — ECMP와 PBR

경로가 갈라지는 원인은 대부분 이 둘 중 하나(혹은 최근 변경 이력).

- **ECMP (Equal-Cost Multi-Path, 동일비용 다중경로)**: 목적지까지 비용이 같은 경로가 여러 개 있을 때, 트래픽을 여러 경로에 분산(대역폭 활용 + 이중화)시키는 라우팅 방식. 보통 출발지/목적지 IP·포트를 해시해서 흐름(flow) 단위로 경로를 정하는데, 장비마다 해시 알고리즘이 다르거나 출발지/목적지가 뒤바뀌면 왕복 경로가 달라질 수 있음.
- **PBR (Policy-Based Routing, 정책 기반 라우팅)**: 목적지 주소만 보고 경로를 정하는 일반 라우팅과 달리, 출발지 IP/애플리케이션/포트 같은 정책에 따라 경로를 강제 지정하는 방식. "이 트래픽은 무조건 이 회선으로" 같은 요구사항 때문에 쓰는데, 방향별로 정책을 다르게 설정하면 의도치 않게 비대칭이 생길 수 있음.

## 해결 방향

1. **경로를 대칭으로 만든다** — 가장 깔끔한 근본 해결책.
2. **방화벽 HA로 세션을 동기화한다** — HA(High Availability, 고가용성)로 방화벽 두 대(액티브-스탠바이/액티브-액티브)를 묶고 세션 테이블을 실시간 동기화. 경로 자체는 안 바꾸지만, 어느 방화벽으로 들어오든 같은 세션 정보를 알고 있게 만들어 우회하는 차선책. 동기화 지연, 구성 복잡도라는 트레이드오프 있음.
3. **해당 구간을 예외/우회 처리한다** — 비권장. 보안 구멍이 될 위험.

## 리눅스 conntrack = 방화벽 세션 테이블

iptables 자체는 규칙 매칭 엔진이고, 상태 추적은 netfilter의 **conntrack** 모듈이 담당.

```bash
conntrack -L   # 현재 세션(연결 상태) 테이블 조회
```

`iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT` 규칙이 바로 이 테이블을 참조하는 것. 팔로알토/ASA 같은 상용 방화벽도 이름만 다르지("세션 테이블", "flow table") 5-tuple 기준으로 허용된 흐름을 기록하는 동일한 개념. 비대칭 라우팅 상황에서는 return 패킷이 들어온 장비의 conntrack에 그 세션이 없어 `INVALID`로 판정되어 드롭됨.

## 블랙홀 · 루프 · TTL · traceroute

- **블랙홀(Blackhole)**: 잘못된 정적 경로/디폴트 루트로 트래픽이 아무 데도 못 가고 폐기되는 상황.
- **라우팅 루프**: 라우터끼리 서로에게 목적지를 떠넘기며 패킷이 뱅뱅 도는 상황.
- **TTL(Time To Live)**: 루프에 걸려도 패킷이 무한정 돌지 않도록, 라우터를 한 홉 지날 때마다 1씩 감소하는 카운터. 0이 되면 패킷 폐기 + 원 발신자에게 "시간 초과" 응답.
- **traceroute**: TTL을 1부터 증가시키며 패킷을 보내 각 홉에서 "시간 초과" 응답을 유도, 경로의 라우터를 홉 순서대로 보여주는 도구.

## 트러블슈팅 절차 — "나가긴 하는데 응답이 없다"

1. 출발지·목적지 양쪽에서 각각 `traceroute` 떠서 경로가 같은지(대칭) 확인.
2. 경로상의 방화벽 세션 테이블에 해당 세션이 한쪽 방향만 있는지 확인.
3. return 패킷이 들어오는 방화벽에 세션이 없다 → 비대칭 라우팅 확정.
4. 최근 라우팅/PBR/ECMP 변경이 있었는지 확인(경로가 바뀐 시점 = 원인 특정).
