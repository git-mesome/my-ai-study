## RDBMS vs NoSQL

**RDBMS**: 데이터를 테이블(표)로 저장하고 테이블 간 **관계(FK)**로 연결. MySQL, PostgreSQL, Oracle 등.
- 스키마 고정(미리 컬럼/타입 정의), SQL + JOIN으로 조회, ACID 강하게 보장

**NoSQL**: 관계형이 아닌 방식의 총칭. 종류가 다양함.

| 종류 | 예시 | 특징 |
|---|---|---|
| 문서형 | MongoDB | JSON 비슷한 문서 단위, 스키마 유연 |
| 키-값 | Redis | 단순·빠름, 캐시로 많이 씀 |
| 컬럼형 | Cassandra | 대용량 쓰기에 강함 |
| 그래프형 | Neo4j | 노드-관계 자체가 데이터 |

- 스키마 유연(문서마다 필드 달라도 됨), 관계 대신 중복 저장(비정규화)이 흔함, 수평 확장에 유리

### 핵심 비교

| | RDBMS | NoSQL |
|---|---|---|
| 스키마 | 고정 | 유연 |
| 데이터 관계 | JOIN | 중복 저장(내장) |
| 일관성 | 강한 일관성(ACID) | 대체로 최종 일관성 |
| 확장 | 수직 확장 위주 | 수평 확장에 유리 |
| 적합한 경우 | 관계 복잡·정합성 중요 (금융, 결제) | 구조 자주 변함, 대용량/빠른 읽기 (로그, 세션, 캐시) |

**실무**: 하나만 쓰기보다 목적별로 혼용하는 경우가 흔함 — RDBMS(핵심 데이터) + Redis(캐싱) + MongoDB(로그성 데이터).

**면접 답변**: "RDBMS는 스키마가 고정되고 트랜잭션 정합성이 중요한 데이터에 적합하고, NoSQL은 스키마가 유연하고 수평 확장이 쉬워 대용량/비정형 데이터에 적합합니다. 실무에서는 목적에 따라 함께 쓰는 경우가 많습니다."

## ACID

트랜잭션이 지켜야 할 4가지 성질.

- **Atomicity(원자성)**: 트랜잭션 내 작업은 전부 성공 or 전부 실패(롤백). 중간 상태 없음.
- **Consistency(일관성)**: 트랜잭션 전후로 데이터가 제약조건(CHECK, FK 등)을 항상 만족.
- **Isolation(격리성)**: 동시 실행되는 트랜잭션들이 서로 간섭 없이 순서대로 실행된 것처럼 보여야 함.
- **Durability(지속성)**: 커밋된 데이터는 서버가 죽어도 사라지지 않음 (WAL 등으로 디스크에 기록해 보장).

- 은행 이체처럼 정합성이 필수인 로직은 A/C/D가 특히 중요.
- [[DLQ/Outbox 패턴]](../cs-study/distributed-systems/260718-dlq-outbox-패턴.md)의 Outbox도 "DB 저장"과 "이벤트 저장"을 한 트랜잭션으로 묶어 A(원자성)를 응용한 사례.
- MongoDB 등 NoSQL은 전통적으로 ACID를 RDBMS만큼 강하게 보장하지 않음.

**면접 답변**: "ACID는 트랜잭션이 지켜야 할 4가지 성질로, 원자성·일관성·격리성·지속성을 의미합니다. RDBMS는 이를 강하게 보장해 정합성이 중요한 데이터에 적합합니다."

## 트랜잭션 격리 수준 (Isolation Level)

격리를 강하게 할수록 정합성은 높아지지만 성능(동시성)은 떨어짐 — 그래서 SQL 표준이 4단계로 구분.

### 격리가 약할 때 발생하는 문제
- **Dirty Read**: 다른 트랜잭션이 아직 커밋 안 한 데이터를 읽음
- **Non-Repeatable Read**: 같은 트랜잭션 안에서 같은 row를 두 번 읽었는데 값이 다름
- **Phantom Read**: 같은 조건으로 두 번 조회했는데 row 개수가 다름

### 4단계

| 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| Read Uncommitted | 발생 | 발생 | 발생 |
| Read Committed | 방지 | 발생 | 발생 |
| Repeatable Read | 방지 | 방지 | 발생(DB마다 다름) |
| Serializable | 방지 | 방지 | 방지 |

- 위로 갈수록 느슨(빠름), 아래로 갈수록 엄격(안전, 느림)
- **PostgreSQL/Oracle 기본값**: Read Committed
- **MySQL(InnoDB) 기본값**: Repeatable Read

### 구현 방식 — MVCC
매번 락으로 막는 대신, PostgreSQL/MySQL(InnoDB)은 **MVCC(Multi-Version Concurrency Control)**로 구현 — 수정 시 기존 값을 덮어쓰지 않고 새 버전을 만들어 각 트랜잭션이 자기 시작 시점 기준 버전을 보게 함. 읽기가 쓰기를 막지 않아 동시성 확보.

### 실무 연결
동시성 문제(예: 재고 동시 차감)는 격리 수준만으로 부족할 수 있어 **비관적 락(SELECT FOR UPDATE)**이나 **낙관적 락(버전 컬럼 체크)**을 명시적으로 추가. 실무 대부분은 기본 격리 수준을 그대로 쓰고, 문제되는 특정 로직에만 락을 건다.

**면접 답변**: "격리 수준은 Read Uncommitted, Read Committed, Repeatable Read, Serializable 4단계가 있고, 낮을수록 빠르지만 Dirty Read 등의 문제가 발생할 수 있습니다. MySQL은 Repeatable Read, PostgreSQL/Oracle은 Read Committed를 기본값으로 씁니다."

## 정규화 (Normalization)

데이터 중복을 줄이고 정합성을 높이기 위해 테이블을 더 작은 단위로 쪼개는 설계 과정.

### 정규화 안 하면 생기는 문제 (이상 현상)
```
orders(order_id, user_name, user_email, product_name, price)  -- 유저 정보가 주문마다 중복 저장
```
- **갱신 이상**: 유저 이메일 바뀌면 그 유저의 모든 주문 row를 다 수정해야 함
- **삽입 이상**: 아직 주문 안 한 신규 유저는 테이블에 넣을 수 없음
- **삭제 이상**: 마지막 주문을 지우면 그 유저 정보 자체가 사라짐

### 정규화로 해결
```
users(user_id, user_name, user_email)
orders(order_id, user_id(FK), product_name, price)
```
유저 정보를 별도 테이블로 분리 + FK 연결 → 위 3가지 이상 현상 해결.

### 단계 (1~3정규형이 실무에서 가장 많이 언급됨)

| 단계 | 규칙 |
|---|---|
| 1NF | 한 컬럼에 값 하나만 (원자값) |
| 2NF | 1NF + 기본키의 일부에만 종속된 컬럼 제거 (부분 함수 종속 제거) |
| 3NF | 2NF + 기본키가 아닌 컬럼끼리의 종속 관계 제거 (이행적 종속 제거) |

암기용: "모든 컬럼은 기본키에게만, 기본키 전체에게, 기본키에게만 의존해야 한다" (Key, Whole Key, Nothing But the Key)

### 반대 개념 — 비정규화(Denormalization)
정규화를 과하게 하면 테이블이 잘게 쪼개져 JOIN이 많아지고 조회 성능이 떨어짐. 조회 성능이 중요한 곳은 일부러 중복을 허용(비정규화)해 JOIN을 줄이기도 함 (예: 게시글 목록에 작성자 이름을 미리 중복 저장해 매번 users JOIN 안 하게 함).

**면접 답변**: "정규화는 데이터 중복을 줄여 갱신/삽입/삭제 이상을 방지하기 위해 테이블을 분리하는 설계 기법입니다. 3정규형까지 실무에서 흔히 적용하고, 과도한 정규화는 JOIN이 늘어나 조회 성능이 떨어질 수 있어 조회가 중요한 경우 일부러 비정규화하기도 합니다."

## JOIN 종류

두 개 이상의 테이블을 공통 컬럼(보통 FK) 기준으로 합쳐서 조회하는 방법.

```
users                    orders
user_id | name           order_id | user_id | amount
1       | 철수            1        | 1       | 10000
2       | 영희            2        | 1       | 20000
3       | 민수            3        | 4       | 30000   ← user_id=4는 users에 없음
```

- **INNER JOIN**: 양쪽 테이블에 다 존재하는 데이터만. 가장 많이 씀.
- **LEFT JOIN(LEFT OUTER JOIN)**: 왼쪽 테이블은 전부 포함, 오른쪽은 매칭되는 것만(없으면 NULL). 실무에서 "전체 목록 + 있으면 추가 정보" 조회에 가장 자주 씀.
- **RIGHT JOIN**: LEFT JOIN 반대. 테이블 순서만 바꾸면 LEFT JOIN으로 대체 가능해 상대적으로 덜 씀.
- **FULL OUTER JOIN**: 양쪽 다 전부 포함, 매칭 안 되는 건 NULL (MySQL은 기본 미지원, LEFT+RIGHT UNION으로 흉내).
- **CROSS JOIN**: 조건 없이 모든 조합(A×B, 카티션 곱). 실수로 조인 조건 빠뜨리면 이 상태가 되어 성능 재앙.
- **SELF JOIN**: 같은 테이블을 자기 자신과 조인 (예: 직원-관리자 같은 계층 구조).

벤 다이어그램으로: `INNER = A∩B`, `LEFT = A 전체`, `RIGHT = B 전체`, `FULL = A∪B`.

**면접 답변**: "INNER JOIN은 양쪽에 매칭되는 데이터만, LEFT JOIN은 왼쪽 테이블 전체를 기준으로 오른쪽이 없으면 NULL로 채웁니다. 실무에서는 LEFT JOIN을 가장 많이 쓰고, RIGHT JOIN은 테이블 순서만 바꾸면 대체 가능해 상대적으로 덜 씁니다."

## 쿼리 실행계획 (Execution Plan)

DB가 SQL을 실제로 어떻게 실행할지에 대한 계획. `EXPLAIN`으로 확인.

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 1;
```

| 항목 | 의미 |
|---|---|
| type | 접근 방식. `ALL`(풀스캔, 느림) vs `ref`/`range`(인덱스 사용, 빠름) |
| key | 실제 사용된 인덱스 (NULL이면 인덱스 미사용 = 위험 신호) |
| rows | 예상 스캔 행 수 (적을수록 좋음) |

**튜닝 흐름**: 느린 쿼리 로그 확인 → `EXPLAIN`으로 실행계획 확인(풀스캔 여부) → WHERE/JOIN 조건 컬럼에 인덱스 추가 → 재확인.

## N+1 문제

연관된 데이터를 조회할 때, 쿼리 1번이면 될 걸 N번 추가로 더 날리는 문제. ORM(JPA/Hibernate)에서 흔히 발생.

```java
List<User> users = userRepository.findAll();  // 쿼리 1번 (5명)
for (User u : users) {
    System.out.println(u.getOrders());  // 유저마다 orders 조회 쿼리가 추가로 나감 (N=5)
}
// 총 1 + 5 = 6번 쿼리, 유저 100명이면 101번
```

**원인**: JPA의 **지연 로딩(Lazy Loading)** — 연관 엔티티를 실제 접근하는 시점에 그때그때 쿼리를 날림. 반복문 안에서 접근하면 매번 쿼리 발생.

**해결**:
- **Fetch Join**: JPQL에서 미리 JOIN으로 한 번에 가져오게 명시 (`JOIN FETCH`)
- **Batch Size 설정** (`@BatchSize`): `IN` 절로 묶어서 여러 개를 한 번에 조회
- **EntityGraph**: 어노테이션으로 즉시 로딩할 연관관계 지정

실행계획만으로는 안 잡힘(쿼리 하나하나는 인덱스를 잘 탈 수 있음) — 쿼리 **횟수** 자체 문제라 쿼리 로그를 같이 봐야 발견됨.

**면접 답변**: "N+1 문제는 연관 엔티티를 지연 로딩으로 조회할 때 반복문에서 접근하는 순간마다 추가 쿼리가 발생해 총 N+1번의 쿼리가 나가는 문제입니다. Fetch Join이나 배치 사이즈 설정으로 한 번에 조회하도록 해결합니다."
