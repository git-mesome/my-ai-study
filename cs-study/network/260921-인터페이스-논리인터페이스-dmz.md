# 인터페이스 · 논리 인터페이스 · 존(DMZ)

> 보안 회사 수습 기간 — 사내 문서 위키 온보딩 자료 학습, 2026-09-21. [VLAN/트렁크 노트](./260916-vlan-트렁크-주소객체.md)의 서브인터페이스 개념과 이어짐.

## 인터페이스(Interface)란

장비가 네트워크에 연결되는 **접점**이자 트래픽이 드나드는 **입구**. 방화벽은 "어느 인터페이스로 들어와서 어느 인터페이스로 나가는가"를 정책 판단의 출발점으로 삼음.

- 인터페이스에는 보통 **IP 주소**와 **소속 네트워크(서브넷)**가 할당됨.
- 방화벽에서는 인터페이스마다 서로 다른 **구간(존)** — 내부망, 인터넷, DMZ 등 — 에 연결됨.

## 물리 인터페이스 vs 논리 인터페이스

- **물리 인터페이스**: 장비에 실제로 달린 포트. `port1`, `eth0`, `ge-0/0/1` 등. 케이블이 물리적으로 꽂히는 자리.
- **논리 인터페이스**: 물리 인터페이스 **위에 소프트웨어로 만든 가상 인터페이스**. IP가 붙고 정책·라우팅의 대상이 된다는 점은 물리와 똑같음.

핵심: **"포트(케이블 구멍)"와 "인터페이스(IP·정책의 단위)"는 1:1이 아니어도 된다.**

### 1. VLAN sub-interface — 포트 1개 → 인터페이스 여러 개

```
        물리 케이블 1가닥 (트렁크)
              │  ← VLAN 10, 20 트래픽이 태그 붙어서 섞여 옴
        ┌─────┴─────┐
        │   eth0    │  물리 인터페이스
        ├───────────┤
        │  eth0.10  │  논리: VLAN 10 → 내부망 (10.0.10.1/24)
        │  eth0.20  │  논리: VLAN 20 → DMZ    (10.0.20.1/24)
        └───────────┘
```

- 케이블 하나로 들어온 트래픽을 **VLAN 태그(802.1Q)**로 나눠 각각 별도 인터페이스로 취급.
- **비유**: nginx 가상 호스트. IP:443 하나로 요청이 와도 `Host` 헤더를 보고 `a.com` / `b.com` 설정으로 나눠 처리하는 것과 같은 구조 (여기서는 헤더 대신 VLAN 태그가 구분자).
- **왜 쓰나**: 방화벽에서 "내부망 → DMZ" 정책을 걸려면 구간마다 인터페이스가 필요한데, 구간 수만큼 물리 포트를 사지 않아도 됨.
- `eth0.10`의 점 뒤 숫자는 인덱스가 아니라 **VLAN ID**.

### 2. 링크 묶음(Aggregate / Bonding) — 포트 여러 개 → 인터페이스 1개

```
  eth0 ─┐
        ├─→ bond0 (IP·정책은 여기에 하나만)
  eth1 ─┘
```

- 물리 포트 여러 개를 묶어 논리 인터페이스 하나로 사용. **비유**: 디스크 여러 개를 하나의 볼륨으로 묶는 RAID.
- **효과**: 대역폭 확대 + 이중화(케이블 하나가 끊겨도 나머지로 계속 동작).
- 벤더별 이름: Linux `bond0`, Cisco `port-channel`(EtherChannel), Juniper `ae0`, FortiGate `Aggregate` 타입.

### 3. 터널 인터페이스 — 물리 포트 없음

- VPN 등 **가상 경로**를 위한 인터페이스. `wg0`(WireGuard), `tun0`(OpenVPN), `gre0` 등.
- 이 인터페이스로 들어간 패킷은 **캡슐화(+암호화)**되어 인터넷을 지나 반대편 끝에서 풀림. 방화벽 입장에서는 "VPN 구간"이라는 인터페이스 하나가 생기는 것.

### Docker와 연결

호스트에서 `ip a`를 치면 `eth0` 외에 `docker0`, `veth1a2b3c…`가 보임. 물리 포트가 아닌데도 IP가 있고 라우팅 대상 — 전부 논리 인터페이스.

```bash
# Linux에서 VLAN sub-interface 만들기
ip link add link eth0 name eth0.10 type vlan id 10
ip addr add 10.0.10.1/24 dev eth0.10
```

## 인터페이스 이름 규칙 — 왜 `eth0`처럼 0이 붙나

이름 = **종류(prefix) + 번호(index)**. 번호는 배열 인덱스처럼 **0부터** 셈.

| 이름 | 종류 | 번호 |
|---|---|---|
| `eth0`, `eth1` | Ethernet 포트 | 첫 번째, 두 번째 |
| `bond0` | 링크 묶음 | 첫 번째 묶음 |
| `wg0` | WireGuard 터널 | 첫 번째 터널 |
| `docker0` | Docker 브리지 | 첫 번째 |
| `lo` | loopback | 하나뿐이라 번호 없음 |

종류별로 번호 규칙이 조금씩 다름:

- **VLAN sub-interface** `eth0.10` — 점 뒤는 인덱스가 아니라 VLAN ID.
- **네트워크 장비** `ge-0/0/1` (Juniper) — `슬롯/모듈/포트` 물리 위치 번호. 0은 "0번 슬롯, 0번 모듈, 1번 포트"처럼 위치를 뜻함.
- **최신 Linux** `enp3s0`, `ens33` — **Predictable Network Interface Names**. 예전 `eth0`은 부팅 시 장치 인식 순서대로 번호가 붙어서, NIC 추가/순서 변경 시 `eth0`과 `eth1`이 뒤바뀌는 문제가 있었음. 그래서 PCI 슬롯 등 하드웨어 위치 기준으로 이름을 고정하게 바뀜. `enp3s0` = "PCI 버스 3번, 슬롯 0의 Ethernet".
- `eth0`이 안 보이고 `enp3s0` 같은 이름만 보여도 정상 — 요즘 Linux 기본값.

## 존(Zone)과 DMZ

방화벽은 인터페이스를 **신뢰 수준별 구간(존)**에 소속시키고, 존 간 이동 트래픽에 정책을 건다.

| 존 | 의미 | 예 |
|---|---|---|
| **trust** | 신뢰하는 구간 | 내부망 (사내 PC, DB) |
| **untrust** | 신뢰할 수 없는 구간 | 인터넷 |
| **DMZ** (DeMilitarized Zone, 비무장지대) | trust와 untrust **사이의 완충 구간**. 공개 서버를 둠 | 웹서버, 메일서버 |

```
 untrust (인터넷) ──▶ [ DMZ: 웹서버, 메일서버 ] ──▶ trust (내부망: DB, 사내 PC)
```

- **왜 두나**: 외부에 공개해야 하는 서버를 내부망에 바로 두면, 뚫렸을 때 내부망 전체가 위험해짐. 그래서 중간에 한 겹 더 두고 공개 서버를 거기에 격리.
- **기본 정책 방향**
  - 인터넷 → DMZ: 필요한 포트만 허용 (예: 443)
  - 인터넷 → 내부망: 차단
  - DMZ → 내부망: 기본 차단, 필요한 것만 허용 (예: 웹서버 → DB 접속). DMZ 서버가 뚫려도 내부망으로 번지지 않게 하려는 것.
- **인터페이스와의 연결**: 위의 `eth0.20` 같은 논리 인터페이스 하나를 DMZ 존에 소속시키는 식으로 구성 → **케이블 하나로도 여러 보안 구간을 나눌 수 있는 이유**.
- 참고: Linux의 firewalld도 존(Zone) 단위 관리 방식 — [네트워크 기초 면접정리](./260816-네트워크-기초-면접정리.md) 참고.

### 존 단위 정책의 이점 — 인터페이스가 늘어나는 상황

존은 **신뢰 수준이 같은 인터페이스를 하나로 묶은 단위**. 정책을 인터페이스가 아니라 존 기준으로 쓰면, 인터페이스가 늘어도 정책을 다시 만들 필요가 없음.

```
[인터페이스 단위 정책]                     [존 단위 정책]
내부망 VLAN 10, 20, 30 → 인터넷            internal 존 = {VLAN 10, 20, 30}
 정책 3개 (인터페이스마다 따로)             정책 1개 (internal → untrust)

VLAN 40 추가 시                            VLAN 40 추가 시
 정책 새로 작성 (4개로)                     VLAN 40을 internal 존에 편입만 하면
 → 빠뜨리면 통신 안 됨                       기존 정책이 자동 적용
```

- 인터페이스 단위 정책은 인터페이스가 늘수록 정책 수가 곱으로 늘어남(출발 N개 × 도착 M개) → 수정 누락·불일치 위험.
- 그래서 **중복 인터페이스가 아니라 "중복 정책"**이 줄어드는 것이 핵심.

#### 서술형 답안 예시 (온보딩 퀴즈 6번)

> 존은 신뢰 수준이 같은 인터페이스들을 하나로 묶은 단위이므로, 정책을 존 단위로 작성하면 같은 성격의 인터페이스마다 동일한 정책을 반복해서 만들 필요가 없어 관리가 쉽고 확장성이 좋습니다. 특히 VLAN sub-interface처럼 인터페이스가 계속 늘어나는 상황에서도, 새 인터페이스를 같은 신뢰 수준의 존에 편입하기만 하면 기존 정책이 그대로 적용되어 정책을 다시 작성하지 않아도 됩니다.

채점 포인트 3가지 (첫 시도는 (1)·(3) 누락으로 **오답**):

1. **전제** — 존은 인터페이스를 *신뢰 수준*으로 묶은 단위
2. **이점** — 정책을 존 단위로 쓰면 확장성·관리성 확보
3. **상황 연결** — 인터페이스가 늘어도 같은 존에 편입만 하면 정책 재작성 불필요

> 서술형 채점은 결론("유지보수 용이")보다 **"왜 그런가"의 인과 사슬**(전제 → 이점 → 문제 상황 적용)을 봄.

#### 5번 문제 답안 예시 (인터페이스의 역할)

> 인터페이스는 방화벽이 네트워크에 연결되는 접점이자 트래픽이 들어오고 나가는 입구입니다. 방화벽은 "어느 인터페이스로 들어와서 어느 인터페이스로 나가는가"를 정책 판단의 출발점으로 삼습니다. 각 인터페이스에는 IP 주소와 소속 네트워크가 할당되고, 내부망·인터넷·DMZ 같은 서로 다른 구간(존)에 연결됩니다.

- 주의: 허용/차단을 **결정**하는 건 정책(Policy)이고, 인터페이스는 정책이 판단할 때 쓰는 **기준점**.
