# 리눅스 기초 정리 — 면접 대비

> ICT 보안/SI 계열 회사 면접 준비 중 정리, 2026-08-17. 리눅스 심화 퀴즈 15문항 결과 정리.

## 예상 질문 흐름

프로세스/스레드 기초 → 시그널/자원 관리 → 파일시스템 → 메모리 → 트러블슈팅 명령어 → 방화벽 순으로 꼬리질문이 이어지는 경우가 많음. 특히 "장애 났을 때 어떤 명령어로 확인하나요?" 류의 실무 트러블슈팅 질문 비중이 높음.

| 주제 | 예상 질문 |
|---|---|
| 프로세스/스레드 | 차이가 뭔가요? 왜 스레드가 더 가벼운가요? |
| 시그널 | SIGKILL과 SIGTERM 차이는? |
| 자원 | 파일 디스크립터가 뭔가요? "Too many open files"는 왜 나나요? |
| 파일시스템 | 하드 링크와 심볼릭 링크 차이는? 파일 권한 755는 뭔가요? |
| 메모리 | 가상 메모리, 스왑, OOM Killer가 뭔가요? |
| 트러블슈팅 | 포트 점유 프로세스는 어떻게 찾나요? 로그는 어디서 보나요? |
| 프로세스 상태 | 좀비 프로세스와 고아 프로세스 차이는? |
| 방화벽 | iptables/firewalld 기본 정책을 어떻게 잡나요? |

## 프로세스 vs 스레드

**프로세스**: 독립적인 메모리 공간(코드/데이터/힙/스택)을 할당받아 실행되는 단위.
**스레드**: 프로세스 내부의 실행 단위로, **같은 프로세스의 코드/데이터/힙을 공유**하고 스택만 각자 가짐.

**스레드가 더 가벼운 이유 — 핵심은 "메모리 공유"**:
- **생성 비용**: 프로세스는 메모리 공간을 통째로 새로 할당해야 하지만, 스레드는 기존 프로세스 메모리를 그대로 쓰고 스택만 추가 할당하면 됨
- **컨텍스트 스위칭 비용**: 프로세스 전환은 메모리 주소 공간(가상 메모리 매핑) 자체를 바꿔야 해서 CPU 캐시(TLB)가 무효화되지만, 같은 프로세스의 스레드 전환은 메모리 공간이 같아 이 비용이 없음
- **통신 비용**: 프로세스 간 통신은 IPC(파이프, 소켓 등)가 필요하지만, 스레드끼리는 메모리를 그냥 공유(단, 이게 race condition의 원인이기도 함)

**면접 답변**: "프로세스는 독립된 메모리 공간을 갖고 스레드는 프로세스 내에서 메모리(코드/데이터/힙)를 공유합니다. 스레드는 메모리 공간을 새로 만들지 않고 공유하기 때문에 생성, 컨텍스트 스위칭, 통신 비용이 모두 낮아 더 가볍습니다."

## 프로세스 상태 전이와 컨텍스트 스위칭

### Running → Waiting은 대부분 "자발적" (I/O 요청)

프로세스가 디스크 읽기, 네트워크 응답, 락 대기 등 **즉시 끝나지 않는 작업을 요청하면 스스로 CPU를 내려놓고 Waiting으로 전환**. (참고: 타이머 인터럽트로 인한 선점은 Running → **Ready**로, Waiting과는 다른 전이.)

### 컨텍스트 스위칭 — 힙이 아니라 CPU 레지스터 상태를 PCB에 저장

컨텍스트 스위칭이 저장/복원하는 건 애플리케이션 데이터(힙)가 아니라, 프로세스 재개에 필요한 **PC(다음 실행 주소), CPU 레지스터 값, 스택 포인터**를 커널의 **PCB(Process Control Block)**에 저장/복원하는 것. 프로세스 간 전환은 메모리 주소 공간(가상 메모리 매핑)까지 바뀌어 캐시(TLB)가 무효화되는 게 큰 비용 — 스레드 전환이 가벼운 이유와 연결됨.

## 시그널 — SIGKILL vs SIGTERM

핵심은 **"프로세스가 시그널을 가로챌(catch) 수 있는가"**.

| | 캐치 가능 여부 | 동작 |
|---|---|---|
| SIGKILL (9) | 불가능 — 커널이 무조건 강제 종료 | 정리(cleanup) 기회 없이 즉시 종료 |
| SIGTERM (15) | 가능 — 핸들러로 가로채 graceful shutdown 구현 가능 | in-flight 요청 마무리, 커넥션 정리 등 |

- **실무 표준 종료 순서**: SIGTERM 전송 → grace period 대기 → 안 죽으면 SIGKILL (Docker `stop`, Kubernetes Pod 종료가 이 순서)
- **`kill` 명령어가 기본으로 SIGTERM을 보내는 이유**: 가장 안전한 방법을 기본값으로 삼기 위함. SIGKILL을 기본값으로 두면 실수로 데이터 정합성이 깨지는 사고가 나기 쉬움.

**면접 답변**: "SIGKILL은 프로세스가 가로챌 수 없는 강제 종료 신호이고, SIGTERM은 핸들러로 가로채 자원 정리 후 스스로 종료할 수 있는 요청 신호입니다. 실무에서는 SIGTERM으로 먼저 정상 종료를 유도하고, 일정 시간 응답이 없을 때만 SIGKILL을 씁니다."

## 파일 디스크립터(FD)

프로세스가 파일/소켓/파이프 같은 I/O 자원에 접근할 때 OS가 부여하는 정수 번호. `0`=stdin, `1`=stdout, `2`=stderr가 기본으로 열려있고, 이후 `3, 4, 5...` 순으로 배정됨. 네트워크 소켓, DB 커넥션도 내부적으로 fd.

**"Too many open files" 에러 원인**: OS의 fd 개수 제한(`ulimit`)을 넘어선 것. 실무에서는 대부분 **fd 누수**(파일/커넥션을 열고 `close()` 안 함, try-with-resources 미사용 등)가 원인.

**확인 명령어**:
- `lsof -p <PID>`: 특정 프로세스가 연 파일/소켓 목록
- `lsof -p <PID> | wc -l`: 개수 세기
- `ulimit -n`: fd 제한값 확인
- `cat /proc/<PID>/limits`: 프로세스별 제한값

## 하드 링크 vs 심볼릭 링크

**inode**: 파일의 실제 데이터/메타데이터가 저장된 구조체. 파일명은 inode 안에 없고 **디렉토리 쪽**에 저장됨 (inode를 가리키는 이름표).

| | 가리키는 대상 | 원본 삭제 시 | 제약 |
|---|---|---|---|
| 하드 링크 | inode(실제 데이터) 직접, 링크 카운트로 관리 | 데이터 안 사라짐 (링크 카운트만 감소) | 같은 파일시스템만, 디렉토리 불가 |
| 심볼릭 링크 | 원본 경로(문자열)를 담은 별도 파일 | 깨진 링크(dangling)가 됨 | 제약 없음, 다른 파일시스템/디렉토리 가능 |

**실무 연결**: 블루/그린 배포에서 `/app/current`를 심볼릭 링크로 두고 배포마다 가리키는 대상만 원자적으로 바꾸는 패턴에 활용.

## 파일 권한 (rwx, chmod 숫자)

`r=4, w=2, x=1`이며 x는 **삭제가 아니라 실행 권한**. `chmod 755`는 소유자=rwx(7), 그룹=r-x(5), 기타=r-x(5) — 그룹/기타는 실행은 되지만 **쓰기(수정)는 불가**.

파일 **삭제 가능 여부는 파일 자체 권한이 아니라, 그 파일이 속한 디렉토리의 쓰기 권한**으로 결정됨 (디렉토리 엔트리를 지우는 것이므로).

## 가상 메모리 / 스왑 / OOM Killer

- **가상 메모리**: 각 프로세스가 독립된 주소 공간을 갖는 것처럼 만드는 추상화. 목적은 **프로세스 간 격리**와 **실제 RAM보다 많은 메모리를 쓴 것처럼 보이게 하는 것**.
- **스왑**: RAM이 부족할 때 안 쓰는 페이지를 **디스크로 밀어내는(Swap Out)** 것 (반대가 아님). 다시 필요해지면 Swap In(페이지 폴트 발생). 스왑이 심하면 "스래싱"으로 성능 급락.
- **OOM Killer**: RAM+스왑이 모두 소진됐을 때, `oom_score`가 **가장 높은(=메모리를 가장 많이 쓰는) 프로세스**를 강제 종료. "안 쓰는 프로세스"가 아니라 "많이 쓰는 프로세스"가 타겟. `/proc/<PID>/oom_score_adj`로 중요 프로세스는 점수를 낮춰 보호 가능.

**실무 연결**: 컨테이너 메모리 limit 초과 시 SIGKILL로 갑자기 죽는 게 OOM Killer 소행인 경우가 많음. `dmesg`에서 "Out of memory: Killed process" 확인이 첫 단계.

### (참고) Java 가상 스레드와의 연결
Java 가상 스레드(Project Loom)도 같은 JVM 프로세스의 가상 주소 공간을 공유하지만, **OS 스레드와 1:1로 매핑되지 않음** — 소수의 실제 OS 스레드("캐리어 스레드")에 다수의 가상 스레드가 올라타 실행되며, I/O 블로킹 시 캐리어 스레드를 즉시 다른 가상 스레드에 양보. 그래서 수백만 개를 만들어도 실제 OS 리소스 부담이 적음.

## df vs du — 범위(scope)의 차이

- **`df`**: 마운트된 파일시스템(파티션) **전체** 기준 사용량/여유공간
- **`du`**: 특정 파일/디렉토리 기준 재귀적 실제 용량 합산

**둘이 안 맞는 대표 원인**: 프로세스가 파일을 연 채로(fd 유지) 있는데 `rm`으로 지우면, 디렉토리 이름표만 지워지고(inode 링크 카운트만 감소) 실제 데이터는 안 지워짐 → `du`(디렉토리 스캔)엔 안 잡히지만 `df`(파일시스템 전체)엔 여전히 잡힘. `lsof | grep deleted`로 확인 가능.

## 포트 점유 프로세스 확인

```bash
lsof -i :8080              # -p(PID)가 아니라 -i(네트워크 인터페이스/소켓)로 포트 지정
netstat -tulnp | grep 8080 # -t TCP, -u UDP, -l LISTEN만, -n 숫자표시, -p 프로세스
ss -tulnp | grep 8080      # netstat보다 최신, 커널 정보 직접 조회라 더 빠름 — 최신 배포판 권장
```

## 로그 확인 — journalctl vs dmesg

- **`journalctl -u <서비스명>`**: systemd 서비스(unit) 로그. `-f`(실시간), `--since`(기간), `-p err`(레벨 필터) 등과 조합.
- **`dmesg`**: **커널 레벨** 메시지. OOM Killer로 죽은 흔적, 하드웨어/디스크 I/O 에러, 세그폴트 등 애플리케이션 로그에 안 남는 저수준 문제 확인용. 디버깅 순서: 애플리케이션 로그(`journalctl`) 확인 → 단서 없으면 `dmesg`로 커널 레벨 확인.

## 리다이렉션 순서 — `2>&1`은 스냅샷이다

리다이렉션은 **왼쪽에서 오른쪽 순서대로** 처리됨. `2>&1`은 "stderr(2)를 지금 stdout(1)이 가리키는 곳으로 맞춰라"는 **그 순간의 스냅샷**.

```bash
command > output.log 2>&1   # ✅ 올바름: 1을 먼저 파일로 보낸 뒤 2를 1에 맞춤 → 둘 다 파일로
command 2>&1 > output.log   # ❌ 실수: 2를 먼저 맞출 때 1은 아직 터미널 → stderr는 터미널에 남음
```

**실무 연결**: `nohup ./app.sh > app.log 2>&1 &` 패턴에서 순서를 반대로 쓰면 에러 로그만 유실되는 사고가 남.

## 좀비 프로세스 vs 고아 프로세스

| | 상태 | 원인 | 문제 여부 |
|---|---|---|---|
| 좀비 | **이미 종료(죽음)**, 프로세스 테이블에 껍데기만 남음 | 부모가 `wait()`을 호출 안 함 | kill로 못 없앰(이미 죽어서 신호 보낼 대상이 없음). 쌓이면 PID 고갈 위험 — 부모 코드 버그의 신호 |
| 고아 | **여전히 실행 중**(살아있음) | 부모가 먼저 종료됨 | init/systemd가 자동 입양(reparenting)해서 정상 처리 — 문제 아님 |

**면접 답변**: "좀비 프로세스는 이미 종료됐지만 부모가 wait()으로 종료 상태를 회수하지 않아 프로세스 테이블에 남아있는 상태이고, 고아 프로세스는 부모가 먼저 종료돼 init에게 입양된, 여전히 실행 중인 정상 프로세스입니다."

## 방화벽 — iptables vs firewalld

- **iptables**: 커널 netfilter를 직접 다루는 저수준 도구. 체인 규칙을 순서대로 평가, 재부팅 시 별도 저장 필요.
- **firewalld**: iptables/nftables 위에 얹힌 관리 레이어. **존(Zone)** 단위로 선언적 관리, `--permanent`로 영구 적용.

**안전한 기본 정책 — 화이트리스트(Default Deny)**: 기본적으로 다 차단하고 필요한 포트만 허용.
```bash
iptables -P INPUT DROP
iptables -A INPUT -i lo -j ACCEPT
iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -j ACCEPT
```
클라우드 Security Group도 동일한 철학 — 기본 전체 차단 후 필요한 포트만 화이트리스트로 개방.

## 반복 오답 패턴 정리

1. **"살아있다/죽어있다" 상태 오판**: 좀비 프로세스를 "계속 살아있는" 것으로 착각 — 실제로는 이미 종료된 상태라 kill이 안 먹힘. 고아 프로세스도 "아무도 안 쓰는"게 아니라 정상적으로 계속 실행 중인 프로세스.
2. **방향 반전**: 스왑을 "가상 메모리를 땡겨온다"고 반대로 이해 — 실제로는 RAM의 안 쓰는 페이지를 디스크로 밀어내는 것. df/du 관계도 마찬가지로 헷갈리기 쉬움.
3. **명령어 옵션 혼동**: `lsof -p`(PID 지정)와 `lsof -i`(포트/네트워크 지정)를 혼용. `kill`에 시그널 없이 실행하면 SIGTERM이 나가는 이유를 다른 도구(Docker/K8s)의 grace period 정책과 혼동.
4. **원인이 아니라 결과만 언급**: "OOM Killer는 안 쓰는 프로세스를 죽인다"(X) — 실제로는 메모리를 가장 많이 쓰는 프로세스를 죽임. "df/du 차이는 물리 디스크 vs 유저 사용량"(X) — 실제로는 전체 파일시스템 범위 vs 특정 디렉토리 범위의 차이.
