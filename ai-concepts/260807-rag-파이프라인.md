# RAG (Retrieval-Augmented Generation) 파이프라인

> 예전에 짧게 공부해봤던 "벡터DB로 유사 검색" 개념을 다시 정리, 2026-08-07

## 정의

질문이 들어오면 다음 순서로 답변을 만드는 파이프라인:

1. **Retrieval(검색)** — 관련 문서를 벡터 DB에서 유사도 검색으로 찾음
2. **Augmented(보강)** — 그 검색 결과를 프롬프트에 끼워넣음
3. **Generation(생성)** — LLM이 그 문서를 근거로 답변 생성

## 왜 필요한가

LLM한테 그냥 바로 물어보지 않는 이유:

1. **내부/사적 정보** — 학습 데이터에 없는 사내 문서, 고객 데이터
2. **최신성** — 학습 컷오프 이후 바뀐 정보 (어제 뉴스, 방금 바뀐 정책)
3. **환각(hallucination) 감소** — 모델이 "기억"에 의존해 지어내지 않고, 실제 문서를 근거로 답하게 함 (grounding)

파인튜닝(모델 재학습)보다 훨씬 싸고 빠름 — 문서만 바꿔 끼우면 됨.

## 방식 비교 — 왜 "필요한 조각만" 넣는가

**방식 A — 그냥 다 넣기 (불가능/비효율)**

사내 위키 문서 1000개, 각 수천 토큰이라 치면:

```
프롬프트 = [문서1 전체] + [문서2 전체] + ... + [문서1000 전체] + 질문
```

→ 컨텍스트 윈도우 초과. 들어간다 쳐도 매번 무관한 문서까지 다 보내는 건 비용/속도 낭비.

**방식 B — RAG (검색해서 필요한 조각만)**

```
질문: "연차 신청 절차 알려줘"
  → 벡터 검색: 1000개 문서 중 관련 있는 상위 3개만 골라냄
  → 그 3개(또는 관련 단락)만 프롬프트에 넣음
```

→ 1000개 문서는 항상 벡터 DB(외부 저장소)에 있음. "이번 질문에 답하는 이번 프롬프트"에는 관련 있는 몇 개만 실시간으로 골라 넣음. 질문이 바뀌면 뽑히는 문서도 바뀜.

## 최소 예제 (의사코드)

```python
def rag_answer(query):
    query_vector = embed(query)                    # 질문을 벡터로 변환
    docs = vector_db.search(query_vector, top_k=3)  # 유사도 검색으로 관련 문서 3개 추출

    prompt = f"""
    다음 문서를 참고해서 질문에 답해줘:
    {docs}

    질문: {query}
    """
    return llm.generate(prompt)
```
