## 공통 패턴 — "개념 → 커뮤니티 구현 → 벤더 네이티브 기능"

이 계열 용어 전부가 같은 3단계를 밟는다.

```
연구/논문/개념 등장 (예: MemGPT 2023.10)
  ↓
커뮤니티가 API 위에 직접 하네스를 짜서 구현 (LangChain Memory, Mem0, 자체 벡터DB 연동)
  ↓
벤더가 검증된 패턴을 자기 제품에 네이티브 기능으로 흡수 (Claude Code Auto Memory, 2026.2)
```

- **툴 엔지니어링**: 사람들이 프롬프트에 "너는 이런 함수를 쓸 수 있다"고 텍스트로 우겨넣던 것 → OpenAI Function Calling(2023 중)으로 네이티브화
- **가드레일**: NeMo Guardrails 같은 서드파티 라이브러리 → Claude Code의 훅(Hook)으로 벤더가 직접 지원
- **메모리**: MemGPT/LangChain Memory/Mem0 → Claude Code Auto Memory(2026.2)

아직 이 3단계 중 "커뮤니티 구현" 단계에 머물러 있는 것도 있다 (LangGraph, GraphRAG 등은 아직 벤더 네이티브 기능으로 완전히 흡수되지 않음) — 이런 공백을 메우는 게 AX Product Engineer 같은 직무의 일감일 가능성이 높다는 힌트.

## 계층 구조 정리 (형제 관계)

```
하네스(Harness) — 전체 시스템
├── 시스템 프롬프트        (프롬프트 엔지니어링이 가로질러 적용)
├── 컨텍스트 관리 ───────── 컨텍스트 엔지니어링
├── 도구 실행 루프 ──┬───── 루프 엔지니어링 (언제/어떻게 멈출지)
│                   └───── 툴 엔지니어링 (도구를 어떻게 설계할지)
├── 권한 체크 ───────────── 가드레일 엔지니어링 (프롬프트 vs 구조적 강제)
├── 메모리 시스템 ────────── 메모리 엔지니어링
└── (여러 에이전트 조합) ── 오케스트레이션, 그 안에서 이벨/그래프 엔지니어링이 품질·검색을 보강
```

- **프롬프트 엔지니어링**은 특정 박스가 아니라 여러 지점(시스템 프롬프트, 사용자 프롬프트, 도구 결과 포맷팅)에 걸쳐 쓰이는 가로지르는 기법
- **세션/에이전트 구분**: 하네스는 고정된 틀, 세션은 그 틀을 실행한 인스턴스, 에이전트는 그 세션이 도구를 써서 스스로 판단·행동하는 패턴을 가리키는 행동 관점 용어. 오케스트레이션에서 서브 에이전트를 부르면 세션 개수만큼 에이전트도 늘어남
