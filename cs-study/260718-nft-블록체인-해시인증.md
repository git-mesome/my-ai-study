# NFT는 사실 필요 없었다 — 블록체인 해시 타임스탬핑으로 파일 인증하기

> 디지털 상품 판매 서비스에 "NFT 붙여야 함" 요구사항을 받고 학습, 2026-07-18

## 문제 상황

디지털 상품(AI 프롬프트, 스킬, PPT/Notion 템플릿) 판매 서비스에 "NFT를 붙여야 한다"는 요구사항이 왔다. 근데 NFT가 정확히 뭔지 몰랐고, 요구사항을 준 사람도 "NFT = 안전한 거래"라는 이미지로만 알고 있었다.

## 오해 바로잡기: NFT ≠ 암호화

처음엔 "NFT는 파일을 암호화해서 인증된 사람만 접근하게 하는 것"이라 생각했는데, 틀렸다.

**NFT(ERC-721)의 실제 정체**: 파일을 잠그는 기술이 아니라, "이 디지털 자산의 소유권이 누구 것인지"를 블록체인에 기록하는 토큰이다.

```
tokenId → owner 주소       (블록체인에 기록, 이게 "소유권")
tokenId → tokenURI          (메타데이터 JSON 위치, 보통 그냥 IPFS/S3 URL)
```

파일 자체는 컨트랙트 안에 없다. 소유권 등기부등본만 체인에 있고, 실물 파일은 여전히 서버나 IPFS에 따로 있다. 그래서 NFT를 붙여도 "우클릭 저장 방지" 같은 건 전혀 안 된다 — NFT가 막는 건 "누가 원본 소유자로 인정받는가"이지 "누가 파일에 접근할 수 있는가"가 아니다.

## 요구사항 좁히기

"NFT 붙여야 함" → 진짜 원하는 게 뭔지 계속 물어본 결과:

1. 처음엔 "재판매/무단공유 방지" 같은 막연한 걱정 → NFT는 콘텐츠 자체를 막는 기술이 아니라서 해결 안 됨
2. 좁혀보니 "다운로드 제한 + 인증서 느낌" → 이건 로그인/결제 기반 접근 제어로 충분, NFT 불필요
3. 더 파보니 "NFT 매매 플랫폼처럼 사고파는 게 아니라, **파일 고유번호를 블록체인 해시처럼 인증**하고 싶다"는 것 → 여기서 문제가 완전히 다르게 재정의됨

## 결론: 필요한 건 NFT가 아니라 "블록체인 해시 타임스탬핑"

3번 요구사항은 ERC-721(NFT 표준)이 아니라 **해시 타임스탬핑(공증)**이라는, 훨씬 가벼운 개념이다.

- **파일 해시(SHA-256)**: 파일 내용에 대한 고유 지문. 1바이트만 바뀌어도 완전히 다른 값이 나옴 → 무결성(위변조 여부) 검증에 사용
- 이 해시값을 **어디에 기록하느냐**가 신뢰도를 가른다:

| 기록 위치 | 신뢰도 | 비용/복잡도 |
|---|---|---|
| 우리 DB에만 저장 | "회사가 조작 가능하다"는 의심 여지 남음 | 거의 0 |
| 퍼블릭 블록체인에 앵커링 | 아무도 못 지움, 진짜 위변조 불가능 | 낮음~중간 |

두 번째가 스테이크홀더가 원한 "블록체인처럼 암호화"에 해당한다. **ERC-721 발행, 지갑 연동, 마켓플레이스, 로열티 같은 NFT 인프라는 전혀 필요 없다.**

## 아키텍처

```
구매 시: 파일 SHA-256 계산 → DB 저장(hash, buyer, product_id, timestamp)
       → (비용 절감) 여러 해시를 머클 트리로 묶어 루트 하나만
         저비용 체인(Polygon)이나 OpenTimestamps(비트코인에 사실상 무료 앵커링)에 기록
검증 페이지: 파일 재업로드 → 해시 재계산 → DB 매칭 + 온체인 기록 링크 제시
다운로드 제한: 해시/블록체인과 별개로 로그인 + presigned URL로 처리 (표준 접근 제어)
```

## 곁다리로 정리한 CS 개념: 해시 vs 대칭키 vs 비대칭키

| | 목적 | 키 필요? | 되돌릴 수 있나 |
|---|---|---|---|
| 해시 함수 (SHA-256) | 지문 생성 (무결성 검증) | 없음 | **불가능** (일방향) |
| 대칭키 암호화 (AES) | 비밀 유지 | 하나의 키 (암호화=복호화 키 동일) | 가능 |
| 비대칭키 암호화 (RSA, ECDSA) | 비밀 유지 or 서명/인증 | 공개키+개인키 쌍 | 가능 |

암호화는 "복호화"가 전제지만, 해시는 되돌리는 개념 자체가 없다. 그래서 해시는 암호화가 아니라 "지문/체크섬"이라고 부르는 게 정확하다.

**비대칭키는 이미 쓰고 있는 셈이라 따로 구현할 필요 없다.** 해시를 블록체인에 앵커링하는 트랜잭션 자체가 회사 지갑의 개인키로 서명돼서 나가기 때문에 (블록체인 SDK가 자동 처리), "이 회사가 이 시점에 이 해시를 기록했다"는 발급 주체 증명이 트랜잭션 서명만으로 이미 충족된다. 별도의 디지털 서명 레이어는, 나중에 "서버/체인 접속 없이 PDF만으로 오프라인 검증" 같은 요구가 생기기 전까진 불필요.
