# 이벨 엔지니어링 (Eval Engineering)

> AI 엔지니어링 용어 타임라인 학습 중 정리, 2026-08-17

## 정의
LLM/에이전트 시스템의 **성능을 어떻게 측정하고 검증할지**를 설계하는 일.

## 왜 필요한가 (일반 SW 테스트와 차이)
전통 소프트웨어는 입력이 같으면 출력이 항상 같아 "정답과 일치하는지"만 확인하면 끝. LLM은 같은 입력도 매번 다른 출력이 나올 수 있고, 정답이 하나로 정해지지 않는 경우가 많아 "맞다/틀리다"가 아니라 **"얼마나 좋은가"**를 측정하는 방법론이 따로 필요하다.

## 평가 방식 종류

### 1. 자동 메트릭 (Automated Metrics)
정답이 명확한 경우 규칙 기반으로 빠르게 채점. 정확도(분류), BLEU/ROUGE(번역/요약, 요즘은 한계로 잘 안 씀), 코드 생성은 유닛 테스트 통과 여부(가장 신뢰도 높음 — 정답이 명확).

### 2. LLM-as-Judge
정답이 하나가 아닌 경우(요약 품질, 답변 자연스러움), 다른 LLM에게 채점 기준(rubric)과 함께 점수를 매기게 함. [멀티에이전트 오케스트레이션](./260817-멀티에이전트-오케스트레이션.md)의 Debate/Voting 패턴처럼, 심사 LLM 하나가 아니라 여러 개를 써서 다수결로 신뢰도를 높인다.

### 3. 사람 평가 (Human Eval)
가장 신뢰도 높지만 느리고 비쌈. 보통 "자동 평가로 대량 스크리닝 + 샘플만 사람이 검증" 조합으로 사용.

## 무엇을 평가하나 (에이전트 기준)

| 대상 | 평가 포인트 |
|---|---|
| 최종 답변 품질 | 정확한가, 유용한가, 안전한가 |
| 도구 선택 | 올바른 도구를 선택했나 ([툴 엔지니어링](./260817-툴-가드레일-엔지니어링.md)과 직결) |
| 경로 효율성 | 불필요하게 많은 스텝/토큰을 쓰지 않았나 |
| 가드레일 준수 | 하지 말아야 할 행동을 안 했나 |

## 오프라인 vs 온라인 평가
- **오프라인**: 미리 만든 테스트 케이스(벤치마크)로 배포 전 검증, CI 파이프라인에 넣기 좋음
- **온라인**: 실제 운영 트래픽에서 실시간 품질 모니터링 (재질문 비율, 클릭/만족도 등)

## 핵심 난제 — "평가 자체가 신뢰할 만한가"
LLM-as-Judge를 쓰면 "평가하는 LLM도 틀릴 수 있다"는 문제가 남는다.
- 심사 기준(rubric)을 최대한 구체적으로 명시
- 여러 심사자 앙상블(다수결)
- 사람이 만든 골든셋(gold set)으로 심사 LLM 자체의 정확도를 주기적으로 검증

## 실무 연결
- RAG 검색 시스템에서 "무관한 질의 코사인 유사도 최고값 ~0.3, 명확 관련 질의 0.43+"처럼 **실측으로 임계값을 정한 것 자체가 이벨 엔지니어링** — 정답이 없는 문제(적절한 유사도 하한)를 실제 데이터로 검증한 사례
- 가드레일 검증: 위험한 요청 모음(Red-teaming 세트)으로 "실제로 다 차단되는지" 자동 테스트하는 것도 Eval의 일종
- 배포 전 회귀 테스트: 프롬프트/모델 변경 시마다 벤치마크로 자동 재검증

## 면접 답변 요약
"이벨 엔지니어링은 LLM 시스템처럼 출력이 매번 다르고 정답이 하나가 아닌 경우, 성능을 어떻게 측정할지 설계하는 분야입니다. 자동 메트릭, LLM-as-Judge, 사람 평가를 조합하고, 특히 LLM-as-Judge는 채점 기준을 구체화하고 여러 심사자로 앙상블해서 신뢰도를 높입니다. 검색 시스템에서 코사인 유사도 임계값을 실측으로 검증한 경험이 이와 같은 맥락입니다."
