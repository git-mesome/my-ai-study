# 네트워크 기초 정리 — 면접 대비

> ICT 보안/SI 계열 회사 면접 준비 중 정리, 2026-08-16

## OSI 7계층 vs TCP/IP 4계층

| OSI 7계층 | 역할 | 대표 프로토콜/장비 | TCP/IP 4계층 |
|---|---|---|---|
| 7 응용(Application) | 사용자와 맞닿는 서비스 | HTTP, FTP, DNS, SMTP | **응용 계층** |
| 6 표현(Presentation) | 인코딩, 압축, 암호화 | TLS, JPEG, ASCII | (응용 계층에 통합) |
| 5 세션(Session) | 세션 수립/유지(체크포인트)/종료, 대화 순서 제어 | RPC | (응용 계층에 통합) |
| 4 전송(Transport) | 종단 간 신뢰성 있는 전달, 포트 구분 | TCP, UDP | **전송 계층** |
| 3 네트워크(Network) | 경로 지정(라우팅), IP 주소 | IP, 라우터 | **인터넷 계층** |
| 2 데이터링크(Data Link) | 같은 네트워크 내 MAC 주소 전달 | 이더넷, 스위치, MAC | **네트워크 액세스 계층** |
| 1 물리(Physical) | 전기/광 신호로 비트 전송 | 케이블, 허브 | (네트워크 액세스 계층에 통합) |

**면접 답변**: OSI 7계층은 통신을 이해/설계하기 위한 이론적 참조 모델, TCP/IP 4계층은 실제 인터넷에서 쓰는 실무 구현 모델. TCP/IP는 세션·표현·응용을 응용 계층으로, 물리·데이터링크를 네트워크 액세스 계층으로 통합해 단순화한 것. 실무에선 TCP/IP로 동작하지만, 장애를 계층별로 세분화해 진단할 땐 OSI 개념이 여전히 유용해서 같이 씀.

- TCP는 사실상 세션 계층 기능(연결 수립 3-way handshake, 종료 4-way handshake)까지 흡수하고 있어서, TCP/IP 모델에 세션 계층이 별도로 없는 이유가 됨.

## DNS / 네임서버 / TLD

- **DNS**: 도메인 이름 ↔ IP 주소 변환. 로컬 캐시 → **리졸버**(보통 ISP 소유, 또는 8.8.8.8/1.1.1.1 같은 퍼블릭 DNS) → **루트 DNS → TLD DNS → 네임서버(권한 있는 서버)** 순으로 질의.
- **ISP**(KT, SKT 등): 인터넷 회선 자체를 제공하는 통신사. Cloudflare와는 역할이 다름 — ISP는 "도로", Cloudflare는 그 위의 부가 서비스(DNS/CDN/보안).
- **네임서버(NS)**: 특정 도메인의 실제 DNS 레코드(A, CNAME 등)를 들고 답해주는 서버. "네임서버를 Cloudflare로 바꾼다" = 그 도메인의 주소록 관리 권한을 Cloudflare에 위임한다는 뜻.
- **TLD(Top-Level Domain)**: 도메인 맨 끝부분(`.com`, `.io`, `.kr`). gTLD/ccTLD/sTLD로 구분.
- **Cloudflare 실사용 흐름**: 도메인 등록기관에서 구매 → Cloudflare에 사이트 추가 → 네임서버를 Cloudflare 걸로 변경(위임) → 서브도메인마다 A/CNAME 레코드 등록 (예: `wisoft.io` 아래 `A.wisoft.io` → 특정 서버 IP).

## MAC vs IP / ARP / 이더넷

- **IP(3계층)**: 계층적 논리 주소. 라우팅 가능, 목적지까지 가는 동안 값이 유지됨.
- **MAC(2계층)**: 평면적(flat) 물리 주소. 라우팅 불가능, 같은 네트워크 안 실제 전달에만 씀. 라우터를 거칠 때마다 값이 바뀜(홉 단위).
- **왜 둘 다 필요한가 (핵심 면접 답변)**: 목적지 IP는 전체 경로 동안 고정되지만, 출발지/목적지 MAC은 라우터를 지날 때마다 그 구간의 다음 장비 것으로 바뀐다. IP는 "최종 목적지"를, MAC은 "다음 한 구간 전달 대상"을 가리키기 때문에 역할이 다르다.
- **ARP(Address Resolution Protocol)**: IP → MAC 변환. 같은 네트워크 안에서 브로드캐스트로 "이 IP 누구야?" 질의 → 유니캐스트로 MAC 응답 → ARP 캐시에 저장. 2~3계층 경계 프로토콜이지만 이더넷 프레임에 실려 동작해서 보통 링크 계층으로 분류.
  - **ARP 스푸핑**: 가짜 ARP 응답으로 중간자 공격(MITM) 하는 기법.
- **이더넷(Ethernet)**: 유선 LAN의 2계층 표준. 프레임 형식·MAC 주소 체계·케이블 신호 규격을 정의. 대표 장비는 스위치. Wi-Fi는 이더넷이 아니라 802.11 규격.

## 서브넷 마스크 / CIDR

- IP 주소를 **네트워크 부분**과 **호스트 부분**으로 나누는 값. `192.168.1.10/24`에서 `/24`는 앞 24비트가 네트워크 부분이라는 뜻.
- **같은 네트워크 판단**: 내 IP와 목적지 IP를 서브넷 마스크로 AND 연산해 네트워크 부분이 같으면 같은 네트워크(ARP로 직접 전달), 다르면 다른 네트워크(게이트웨이로 전달) → 라우팅 판단의 근거.
- **CIDR = Classless Inter-Domain Routing**. 클래스(A/B/C) 고정 크기 방식의 낭비를 없애고 원하는 크기로 자유롭게 대역을 나누기 위해 도입.
- **/32**: 호스트 부분 0비트 = IP 1개만 지정. 방화벽 규칙에서 "이 IP 하나만 허용/차단"할 때 사용. NAT으로 여러 사용자가 공인 IP 하나를 공유하는 경우, 외부 방화벽 입장에서는 그 공인 IP 하나만 보이므로 `/32`로 충분.
- **`/24`의 의미(헷갈리기 쉬움)**: `/24`는 **호스트 비트가 아니라 네트워크 비트가 24개**라는 뜻. 남는 호스트 비트는 32-24=8개 → 2⁸=256개 주소 중 네트워크 주소(`.0`)와 브로드캐스트 주소(`.255`) 2개를 뺀 **254개가 실사용 가능 호스트**.

## TCP vs UDP

| | TCP | UDP |
|---|---|---|
| 연결 방식 | 연결 지향 (3-way handshake) | 비연결형 |
| 신뢰성 | 순서 보장, 재전송, 흐름/혼잡 제어 | 없음 |
| 속도 | 상대적으로 느림 (확인 절차 오버헤드) | 빠름 |
| 대표 사용처 | HTTP, FTP, 이메일 (데이터 손실 안 됨) | DNS, 실시간 스트리밍/화상회의/게임 (지연보다 실시간성) |

- HTTP/3(QUIC)는 UDP 기반이지만 자체적으로 신뢰성을 구현해 TCP handshake 지연 문제를 해결.

## 라우팅

- **라우팅**: 3계층 핵심 역할. 목적지 IP가 다른 네트워크일 때 최적 경로를 찾아 전달.
- 흐름: 목적지가 내 네트워크 밖이면 게이트웨이(라우터)로 전달 → 라우터가 **라우팅 테이블**(목적지 대역별 다음 홉)을 보고 다음 라우터로 전달 → 반복 → 목적지 네트워크 도착 후 ARP로 최종 MAC 확인.
- **정적 라우팅**(수동 설정) vs **동적 라우팅**(RIP, OSPF, BGP 등으로 라우터끼리 자동 경로 교환 — 인터넷 전체는 BGP로 움직임).
- **ARP vs 라우팅**: ARP는 같은 네트워크 안 MAC 찾기, 라우팅은 다른 네트워크로 넘어갈 경로 찾기.
- **라우팅 테이블 조회 방식**: 목적지 IP와 "정확히 일치"하는 항목을 찾는 게 아니라 **가장 구체적으로 일치하는 대역(Longest Prefix Match)**을 찾음. 일치하는 구체적 대역이 없으면 `0.0.0.0/0`(**기본 경로, Default Route**)이라는 catch-all 규칙으로 보냄 — 집 공유기가 모르는 목적지를 전부 ISP 방향으로 던지는 게 이 예시. 기본 경로조차 없으면 패킷을 버리고 출발지에 ICMP "Destination Unreachable" 응답.
- **순서 정리**: ① 라우팅 테이블로 "다음 홉 IP" 결정(3계층) → ② ARP로 그 IP의 MAC 주소 확인(2계층) → ③ 실제 프레임 전송.

## NAT (Network Address Translation)

- 사설 IP 여러 개를 공인 IP 하나로 내보낼 때, IP만 바꾸는 게 아니라 **포트까지 같이 바꿔치기**(정확히는 PAT/NAPT)해서 여러 기기를 구분함.
- NAT 테이블 예: `192.168.0.2:5000(노트북) → 1.2.3.4:40001`, `192.168.0.3:6000(핸드폰) → 1.2.3.4:40002`. 응답이 40001로 오면 노트북 것, 40002로 오면 핸드폰 것으로 되돌려 매핑.
- 부수 효과: 외부에서 공인 IP만 보이고 내부 개별 기기 IP는 안 보여서 방화벽 비슷한 은닉 효과.
- **포트포워딩**: "이 포트로 들어오는 건 무조건 이 내부 기기로 보내라"고 NAT 테이블에 고정 규칙을 미리 박아두는 것 (예: 집 공유기에서 외부 접속을 특정 내부 서버로 연결).
- **포트포워딩 vs AWS Security Group**: 포트포워딩은 주소/포트를 실제로 바꿔주는 **NAT(번역)**, Security Group은 이미 공인 IP를 가진 인스턴스에 대해 "통과시킬지 말지"만 정하는 **필터(방화벽 규칙)**. 하는 일이 다름 — 번역 vs 필터링.

## VPN (Virtual Private Network)

- 물리적으로 떨어진 두 기기를 **암호화된 가상 터널**로 연결해 "같은 사설망에 있는 것처럼" 만드는 기술.
- **Remote Access VPN**: 개인 기기가 원격으로 사설망(회사 내부망, 집 서버)에 접속 (재택근무, 원격 서버 관리).
- **Site-to-Site VPN**: 서로 다른 지사의 네트워크 전체를 묶어 하나의 사내망처럼 구성 (기업 인프라).
- **전통적 상업 VPN(NordVPN 등)**: 모든 트래픽을 VPN 회사의 중앙 서버 하나로 몰아서 내보냄 → 그 서버 위치에 따라 접속 리전이 바뀜(우회 접속 효과).
- **Tailscale 같은 메시(Mesh) VPN**: 중앙 서버를 거치지 않고 참여 기기끼리 WireGuard 기반으로 **직접 P2P 터널**을 뚫음. 목적이 "우회"가 아니라 "여러 기기를 하나의 사설망처럼 안전하게 묶는 것" — 포트포워딩으로 인터넷에 노출시키지 않고도 원격 접속 가능.

## HTTPS/TLS 핸드셰이크 — 대칭키+비대칭키 하이브리드

- **대칭키만 쓰면**: 빠르지만 "이 비밀 키를 처음에 어떻게 안전하게 나눠 가지냐"는 키 교환 문제가 남음 (평문 전송 시 도청으로 탈취 가능).
- **비대칭키만 쓰면**: 키 교환은 안전하지만 연산이 무거워서 대용량 트래픽 전체를 암호화하기엔 느림.
- **하이브리드 방식**: 비대칭키(서버 공개키)로 **대칭키(세션키)를 안전하게 교환하는 데만** 사용 → 이후 실제 데이터 전송은 빠른 대칭키로 처리.
- **공개키는 반드시 검증해야 함** — 검증 안 하면 공격자가 자기 공개키를 서버인 척 건네는 MITM이 가능해짐. 그래서 **CA(인증 기관)가 서명한 인증서**로 공개키의 진위를 확인하는 절차가 필수 (브라우저의 "안전하지 않은 연결" 경고가 이 검증 실패 상황).

## 로드밸런서 (Load Balancer)

- **필요한 이유**: 1차로는 트래픽을 여러 서버로 분산해 서버 한 대의 부하 한계를 넘기지 않기 위함(수평 확장의 전제 조건). 2차로 헬스체크를 통해 응답 없는 서버를 트래픽 분배 대상에서 제외하는 가용성(Failover) 기능도 겸함.
- **Round Robin**: 서버들에 순서대로 균등하게 트래픽 분배. 서버 스펙이 다 같을 때 적합.
- **Weighted(가중치 기반)**: 서버 스펙 차이가 있을 때(예: 8코어 vs 2코어), 비율을 다르게 줘서 스펙 좋은 서버에 트래픽을 더 많이 보냄. Round Robin은 스펙 차이를 고려 안 해서 저스펙 서버에 과부하를 줄 수 있음.

## 방화벽

- **패킷 필터링(3~4계층)**: 출발지/목적지 IP, 포트, 프로토콜만 보고 허용/차단.
- **Stateful 방화벽**: TCP handshake 상태를 추적해 정상 연결 흐름만 허용 (실무 대부분 이 방식).
  - **Stateless와의 차이(외부 요청 → 응답 예시)**: Stateless는 각 패킷을 독립적으로 규칙과만 비교해서, 나가는 요청을 허용해도 **돌아오는 응답에 대한 별도 inbound 규칙을 직접 만들어야** 함. Stateful은 상태 테이블에 "내가 시작한 연결"로 기록해두고 그 응답을 **자동으로 허용** — 반대로 시작한 적 없는 연결의 뜬금없는 ACK는 상태 테이블에 없으니 차단.
- **L7 방화벽/WAF(7계층)**: HTTP 요청 내용(URL, 헤더, body)까지 검사해 SQL Injection, XSS 같은 애플리케이션 공격 차단.
- 기본 원칙: **Default Deny** (기본적으로 다 막고 필요한 것만 화이트리스트로 허용).
- 배치 위치별: 네트워크 방화벽(경계 전체) / 호스트 방화벽(개별 서버·PC) / 클라우드 방화벽(AWS 보안그룹 등).

### iptables/firewalld/UFW — 저수준 규칙 엔진 vs 그 위의 관리 도구

- **iptables**: 커널 netfilter를 직접 다루는 저수준 도구. 체인(Chain) 규칙을 순서대로 평가, 재부팅 시 별도 저장(`iptables-save`) 필요.
- **firewalld**: iptables/nftables 위에 얹힌 관리 레이어. **존(Zone)** 단위로 선언적 관리, `--permanent`로 영구 적용. 주로 RHEL/CentOS 계열 기본.
- **UFW(Uncomplicated Firewall)**: 마찬가지로 iptables(최신 Ubuntu는 nftables 백엔드)를 대신 다뤄주는 **프론트엔드**. `ufw allow 22/tcp` 같은 명령이 실제로는 내부적으로 iptables 규칙을 생성함(`iptables -L`로 UFW가 만든 체인 확인 가능). 주로 Ubuntu/Debian 계열 기본.
  - **UFW도 Stateful**: 기본 설정(`/etc/ufw/before.rules`)에 `-m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT`가 이미 포함돼 있어, 나가는 연결의 응답 트래픽을 별도 규칙 없이 자동 허용함 — iptables의 `state`/`conntrack` 모듈과 동일한 원리.
- **정리**: 셋 다 최종적으로는 커널의 netfilter(또는 nftables)를 조작하는 것이고, firewalld/UFW는 그걸 사람이 쓰기 쉽게 감싼 도구. "배포판별 기본 방화벽 도구가 다를 뿐, 근본 메커니즘(stateful 패킷 필터링)은 동일하다"가 핵심.

### NGFW (Next-Generation Firewall, 차세대 방화벽)

패킷 필터링·Stateful·L7/WAF 기능을 한 장비에 통합하고, 추가 기능까지 얹은 방화벽.

- **DPI(Deep Packet Inspection)**: 패킷 내용까지 검사 (WAF 역할 포함)
- **애플리케이션 인식**: 포트 번호가 아니라 실제 트래픽이 어떤 앱인지 식별해 앱 단위로 차단/허용 (예: 같은 443 포트라도 특정 앱만 차단)
- **IPS(침입 방지 시스템)** 내장: 알려진 공격 시그니처 탐지 시 자동 차단
- **위협 인텔리전스 연동**: 알려진 악성 IP/도메인 실시간 차단
- **SSL Inspection**: 암호화 트래픽도 복호화해서 내용 검사 후 재암호화

**등장 배경**: 요즘 트래픽 대부분이 443(HTTPS) 포트로 오가서 포트 기반 구분이 무의미해짐 → 내용/애플리케이션 기반 제어가 필요해져 DPI·앱 인식·IPS를 통합한 NGFW가 표준이 됨. 대표 제품: Palo Alto Networks, Fortinet(FortiGate), Cisco Firepower.

### XSS (Cross-Site Scripting)

- 공격자가 악성 스크립트를 웹페이지에 심어 다른 사용자 브라우저에서 실행되게 하는 공격. 쿠키/세션 토큰 탈취가 주 목적.
- **Stored XSS**(DB에 저장돼 모든 조회자에게 실행) vs **Reflected XSS**(URL 파라미터로 클릭한 사람에게만 즉시 실행).
- 방어: 입력값 이스케이프(`<` → `&lt;`), CSP 헤더, WAF 탐지.

## 계층별 장애 트러블슈팅

아래 계층부터 순서대로 좁혀나간다 — 아래 계층이 안 되면 위 계층 확인은 무의미.

```
1. ping <목적지 IP>          → 실패 시 3계층 이하(라우팅/물리/ARP) 문제
2. telnet/nc <IP> <포트>     → 실패 시 4계층 문제 (방화벽 차단, 서비스 미기동)
3. curl -v <URL>             → 에러 시 7계층 문제 (애플리케이션 버그, DNS는 nslookup/dig로 별도 확인)
```

| 계층 | 증상 | 확인 도구 |
|---|---|---|
| 1 물리 | 인터넷 아예 안 뜸 | 링크 LED, 케이블 교체 |
| 2 데이터링크 | 같은 네트워크 내 통신 안 됨 | `arp -a`, 스위치 포트/VLAN |
| 3 네트워크 | 외부(인터넷)만 안 됨 | `ping`, `traceroute`/`tracert` |
| 4 전송 | 특정 포트/서비스만 안 됨 | `telnet`, `nc -zv` |
| 7 응용 | 접속은 되는데 에러/느림 | `nslookup`/`dig`, `curl -v`, 서버 로그 |

## 2026-08-17 복습 결과 — 반복 오답 재점검

- **TCP/IP 4계층 최하위 계층 이름("네트워크 액세스 계층")**: ✅ 이번엔 정확히 맞힘. 해결된 것으로 판단.
- **ARP에서 같은/다른 네트워크 판단 후 "누구의 MAC을 묻는지"**: ❌ 여전히 반대로 답함 (같은 네트워크 → 목적지 호스트 MAC / 다른 네트워크 → 게이트웨이 MAC인데, 이번에도 뒤바꿔 답함). 다음에도 계속 우선 재점검 필요.
- 새로 발견된 반복 패턴: **방향 반전형 오답**이 계속 나옴 — 스왑(가상메모리→디스크 vs 디스크→가상메모리), df/du, ==/equals, 대칭키/비대칭키 역할, CIDR의 네트워크 비트/호스트 비트 등에서 "두 대상 중 반대쪽으로 착각"하는 경향이 Java/리눅스 파트에서도 공통적으로 관찰됨.
