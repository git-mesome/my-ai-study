## JVM 런타임 데이터 영역

객체 인스턴스는 **힙(Heap)**에 생성됨. 힙/스택만 있는 게 아니라 4가지 영역으로 나뉨.

| 영역 | 저장 내용 | 공유 여부 |
|---|---|---|
| 힙(Heap) | 객체 인스턴스, 배열 | 모든 스레드 공유 |
| 메소드 영역(Method Area) | 클래스 메타데이터, 필드/메소드 정보(바이트코드), 런타임 상수 풀, **static 변수** | 모든 스레드 공유 |
| 스택(Stack) | 메소드 호출 프레임(지역변수, 파라미터) | 스레드마다 별도 |
| PC 레지스터 | 현재 실행 중인 명령어 주소 | 스레드마다 별도 |
| 네이티브 메소드 스택 | JNI로 호출되는 네이티브 코드용 | 스레드마다 별도 |

- **static 변수가 메소드 영역에 있는 이유**: "전역"이라서가 아니라, 인스턴스 여부와 무관하게 **클래스당 하나만 존재**하는 클래스 레벨 데이터라서 클래스 메타데이터와 같은 곳에 저장됨. 모든 스레드가 공유하므로 멀티스레드 환경에서 static 변수 동시 접근 시 race condition 위험이 있음.

**면접 답변**: "JVM 런타임 데이터 영역은 힙, 스택, 메소드 영역, PC 레지스터, 네이티브 메소드 스택으로 나뉩니다. 객체 인스턴스는 힙에 생성되고, static 변수는 클래스 메타데이터와 함께 메소드 영역에 저장됩니다."

## GC (가비지 컬렉션)

### Young/Old 영역을 나누는 이유 — 약한 세대 가설(Weak Generational Hypothesis)

**대부분의 객체는 생성되고 금방 죽는다**는 경험적 관찰이 근거. 그래서:
- **Young 영역**: 새 객체가 생성되는 곳. 좁아서 자주 스캔(**Minor GC**)해도 비용이 적음.
- Young에서 몇 번 GC를 버티고 살아남은 객체만 **Old 영역으로 승격(Promotion)**.
- **Old 영역**: 오래 살 걸로 검증된 객체들이 모여 있어 스캔 빈도가 낮음(**Major/Full GC**).

영역을 나눈 목적은 "삭제 경쟁"이 아니라 **객체 수명 패턴에 맞춰 스캔 빈도를 다르게 가져가 GC 비용을 줄이는 것**.

### GC 알고리즘 3종

| 종류 | 방식 | 목표 |
|---|---|---|
| Serial GC | 스레드 1개로 처리, Stop-the-World | 소규모/단일 코어 환경 |
| Parallel GC (Java 8 기본) | 여러 스레드로 병렬 처리, 여전히 Stop-the-World | 처리량(Throughput) 최적화 |
| G1 GC (Java 9+ 기본) | 힙을 작은 Region으로 쪼개 가비지 많은 곳부터 회수 | 지연시간(Latency) 예측·최소화 |

**실무 연결**: "Full GC 때문에 응답 지연 튄다"는 이슈는 Old 영역이 꽉 차 Major/Full GC가 도는 상황. Young 영역 크기(`-Xmn`)나 GC 종류(`-XX:+UseG1GC`) 튜닝으로 대응.

**면접 답변**: "GC는 Young/Old로 힙을 나눠, 대부분 금방 죽는 객체를 Young에서 자주 청소하고 오래 살아남은 객체만 Old로 승격시켜 스캔 비용을 줄입니다. G1 GC는 힙을 Region 단위로 쪼개 가비지가 많은 곳부터 회수해 지연시간을 최소화합니다."

## == vs equals(), hashCode()

| | 비교 대상 |
|---|---|
| `==` | 객체 **참조(주소값)** 비교 |
| `.equals()` | `Object` 기본 구현은 `==`와 동일(주소 비교)하지만, `String` 등은 오버라이드해서 **내용(값)** 비교 |

```java
String a = new String("hello");
String b = new String("hello");
a == b;       // false — 다른 객체
a.equals(b);  // true  — String이 내용 비교하도록 오버라이드함
```

**`equals()` 오버라이드 시 `hashCode()`도 같이 오버라이드해야 하는 이유**: "equals()가 true인 두 객체는 반드시 같은 hashCode()를 반환해야 한다"는 계약(contract) 때문. `HashMap`/`HashSet`은 `hashCode()`로 버킷을 정하고 그 안에서 `equals()`로 비교하는데, 이 규칙이 깨지면 논리적으로 같은 객체가 다른 버킷에 들어가 `contains()`/`get()`이 존재하는 데이터도 못 찾는 버그가 생김.

**면접 답변**: "==는 참조(주소)를 비교하고 equals()는 내용을 비교하도록 오버라이드될 수 있습니다. equals()를 오버라이드하면 hashCode()도 같이 오버라이드해야, HashMap 등 해시 기반 컬렉션에서 논리적으로 같은 객체가 같은 버킷에 들어가 정상 조회됩니다."

## 컬렉션 내부 동작

### HashMap — put()과 해시 충돌 처리

1. `key.hashCode()`로 해시값 계산 → 버킷 인덱스 결정 → 해당 버킷에 저장
2. **해시 충돌**(다른 key가 같은 버킷에 배정) 시:
   - Java 7까지: 같은 버킷 안에서 **연결 리스트**로 연결 (최악 O(n))
   - Java 8부터: 버킷 안 데이터가 8개 넘으면 **red-black 트리**로 전환 (O(log n)로 개선)
3. (참고) **리해싱(rehashing)**: 충돌 처리와 별개로, 데이터가 많이 차서 load factor를 넘으면 버킷 배열 크기를 2배로 늘리고 재배치하는 것.

### HashMap vs LinkedHashMap vs TreeMap

| | 순회 순서 | 내부 구조 | 조회 속도 |
|---|---|---|---|
| HashMap | 없음(불특정, 버킷 물리 위치 순) | 버킷 배열 + (리스트/트리) | O(1) 평균 |
| LinkedHashMap | **삽입 순서** 유지 | HashMap + 별도 이중 연결 리스트 | O(1) 평균 |
| TreeMap | **키 정렬** 순서 | Red-Black Tree 1개 | O(log n) — HashMap보다 느림 |

### ArrayList vs LinkedList

| | 내부 구조 | 중간 삽입 | 인덱스 접근(`get(i)`) |
|---|---|---|---|
| ArrayList | 배열 | 느림 — 이후 요소 전부 한 칸씩 이동 | O(1) |
| LinkedList | 노드 링크 | 빠름 — 노드 연결만 변경 | O(n) — 앞에서부터 탐색 |

**실무**: 조회가 잦으면 ArrayList(기본 선택), 중간 삽입/삭제가 빈번하면 LinkedList.

**면접 답변**: "HashMap은 해시 충돌 시 Java 8부터 버킷 내 데이터가 8개를 넘으면 연결 리스트를 red-black 트리로 전환해 조회 성능을 개선합니다. 순서가 필요하면 LinkedHashMap(삽입 순서)이나 TreeMap(정렬 순서)을 씁니다."

## String — 불변(Immutable)과 성능

- **불변인 이유**: "클래스라서"가 아니라 **설계 의도**. 내부 필드가 `final`이고 값 변경 메소드가 없음. String Pool 안전한 공유, 멀티스레드 동기화 없이 공유 가능, HashMap 키로 쓸 때 hashCode 불변 보장 등의 이점 때문.
- **`+` 반복 사용 시 성능 저하 이유**: 이어붙일 때마다 이전 내용을 통째로 복사해 새 객체를 생성 → 반복문에서 n번 하면 O(n²)에 가까운 비용.
- **`StringBuilder`**: 내부에 가변 char 배열(버퍼)을 유지하며 `append()`로 그 버퍼에 바로 추가 → O(n)에 가까운 비용으로 해결.

**면접 답변**: "String은 내부 필드가 final이라 값을 바꿀 수 없고, +로 이어붙이면 매번 새 객체를 생성하며 이전 내용을 복사해 반복문에서 O(n²) 비용이 듭니다. StringBuilder는 가변 버퍼에 append하는 방식으로 이 문제를 해결합니다."

## 제네릭과 타입 소거 (Type Erasure)

- **타입 소거가 생긴 이유**: 런타임에 타입을 몰라서가 아니라 **하위 호환성** 때문. Java 5에서 제네릭이 도입될 당시 이미 제네릭 없는 바이트코드가 세상에 깔려 있었고, JVM 바이트코드 포맷 자체가 제네릭 타입을 담게 설계되지 않았음. 그래서 **컴파일 타임에만 타입 체크**하고, 컴파일된 바이트코드에서는 타입 정보를 지워 호환성을 유지.
- **`new T()`가 안 되는 이유**: 개발자가 몰라서가 아니라, 타입 소거로 인해 **컴파일된 바이트코드에 T의 실제 타입 정보가 남아있지 않아서** JVM이 무슨 클래스를 생성할지 알 수 없기 때문.
- **우회 방법**: `Class<T> clazz` 파라미터를 받아 `clazz.getDeclaredConstructor().newInstance()` 사용, 또는 `Supplier<T>` 팩토리 전달.

**면접 답변**: "제네릭은 Java 5 도입 당시 하위 호환성을 위해 컴파일 타임에만 타입 체크를 하고 런타임 바이트코드에서는 타입 정보를 지우는 타입 소거 방식으로 구현됐습니다. 그래서 런타임에 T의 실제 타입 정보가 없어 new T() 같은 코드는 작성할 수 없습니다."

## 예외 처리

### Checked vs Unchecked

핵심 차이는 "언제 발생하냐"가 아니라 **"컴파일러가 처리를 강제하냐"**. 모든 예외는 런타임에 발생함.

| | 상속 | 컴파일러 강제 | 예시 |
|---|---|---|---|
| Checked | `Exception` (RuntimeException 제외) | try-catch 또는 throws 필수, 안 하면 컴파일 에러 | IOException, SQLException |
| Unchecked | `RuntimeException` | 강제 없음 | NullPointerException, IllegalArgumentException |

### try-with-resources

"조건 성립 안 되면 catch되는 것"이 아니라 **자원(Resource) 자동 close() 기능**. `try(...)` 괄호 안에서 선언한 `AutoCloseable` 자원은 정상 종료든 예외든 상관없이 블록이 끝나면 자동으로 닫힘 — 수동 `finally` close() 코드와 자원 누수 위험을 없앰.

**면접 답변**: "Checked Exception은 컴파일러가 처리를 강제하는 예외이고 Unchecked는 강제하지 않는 RuntimeException 계열입니다. try-with-resources는 AutoCloseable 자원을 try 블록 종료 시 자동으로 닫아줘 자원 누수를 방지합니다."

## 멀티스레딩

### Thread 상속 vs Runnable 구현

Java는 다중 상속이 안 되므로, `Thread`를 상속하면 다른 클래스를 상속할 수 없게 됨. `Runnable`은 인터페이스라 다른 클래스 상속과 병행 가능 + "실행할 작업"과 "스레드"의 역할이 분리돼 재사용성이 높음. → **Runnable(또는 Callable) + ExecutorService** 조합이 실무 표준.

### synchronized vs volatile

| | 해결하는 문제 | 비고 |
|---|---|---|
| `volatile` | **가시성(Visibility)** — CPU 캐시가 아닌 메인 메모리에서 직접 읽고 쓰게 강제 | 원자성은 보장 안 함 (`count++`는 여전히 위험) |
| `synchronized` | **원자성(상호 배제) + 가시성** 둘 다 | 락 대기로 volatile보다 비용 큼 |

### ExecutorService (스레드풀)

- **필요한 이유**: `new Thread()`는 코드 길이 문제가 아니라, **스레드 생성 자체가 OS 리소스를 쓰는 무거운 작업**이라 무한정 생성하면 리소스 고갈로 서버가 죽을 수 있음.
- **핵심 파라미터**: `corePoolSize`(기본 유지 스레드 수), `maximumPoolSize`(최대), `keepAliveTime`(core 초과 여분 스레드의 유휴 종료 시간)
- **동작 순서**: core 스레드 여유 있으면 즉시 실행 → 다 찼으면 **작업 큐**에 대기 → 큐도 꽉 차면 max까지 스레드 추가 생성 → 그것도 다 차면 거부 정책(RejectedExecutionHandler) 적용
- **재사용의 의미**: 스레드가 작업 끝나고 죽는 게 아니라 큐에서 다음 작업을 꺼내 계속 실행.

### ConcurrentHashMap

`Collections.synchronizedMap()`은 맵 전체를 하나의 락으로 잠가 병목이 생기지만, `ConcurrentHashMap`은 **버킷 단위로 락을 잘게 쪼개**(Java 8부터는 세그먼트 대신 버킷/노드 단위) 서로 다른 부분을 동시에 수정 가능. 읽기는 대부분 락 없이도 가능.

**면접 답변**: "volatile은 가시성만, synchronized는 가시성과 원자성을 모두 보장합니다. 스레드풀은 스레드 생성 비용이 커서 미리 만든 스레드를 재사용하려고 쓰고, ConcurrentHashMap은 맵을 잘게 쪼개 부분별로 락을 걸어 synchronizedMap보다 동시성이 높습니다."

## 인터페이스 vs 추상 클래스, default 메소드

- **핵심 차이**: 클래스는 `extends` 하나만 가능하지만 `implements`는 여러 개 가능(다중 구현). 여러 역할(Capability)을 가져야 하면 인터페이스, 공통 상태/기본 동작을 공유하는 확실한 부모-자식(IS-A) 관계면 추상 클래스.
- **default 메소드 도입 이유**: 인터페이스에 새 추상 메소드를 추가하면 기존 구현체가 전부 컴파일 에러 남 (예: Java 8에서 `Collection`에 `forEach()`, `stream()` 추가 시 전 세계 배포된 구현체가 깨질 뻔함). `default`로 기본 구현을 인터페이스 자체에 넣어 기존 구현체를 안 깨뜨리면서 새 메소드 추가 가능.

## 람다와 Stream

- **람다가 구현하는 것**: "익명 클래스"가 아니라 **함수형 인터페이스(Functional Interface)** — 추상 메소드가 하나뿐인 인터페이스(`Runnable`, `Comparator`, `Function` 등). 컴파일 방식도 익명 클래스와 다름(`invokedynamic` 사용).
- **Stream 중간 연산이 지연(lazy)되는 이유**: "최종연산이 있어서"가 아니라 **성능 최적화 설계**.
  - 데이터를 **한 번만 순회**하기 위해 (중간 연산마다 컬렉션을 새로 안 만듦)
  - **Short-circuiting** 가능 (`findFirst()` 등 조건 맞으면 나머지 원소는 처리 안 함)

**면접 답변**: "람다식은 추상 메소드가 하나뿐인 함수형 인터페이스를 구현한 것입니다. Stream의 중간 연산이 지연 실행되는 이유는 최종 연산 호출 시점에 데이터를 한 번만 순회하며 파이프라인을 적용하고, 조건에 따라 불필요한 연산을 생략(short-circuit)하기 위한 성능 설계입니다."

## 다형성 (Polymorphism)

단순히 "여러 클래스로 나눈 것"이 아니라, **여러 하위 타입을 상위 타입(인터페이스/부모클래스) 하나로 다루면서 실제 구현체는 런타임에 결정(동적 바인딩)되게 하는 것**.

```java
interface PaymentMethod { void pay(int amount); }
class CardPayment implements PaymentMethod { ... }
class CashPayment implements PaymentMethod { ... }

PaymentMethod method = getPaymentMethodFromUser();
method.pay(10000); // 어떤 구현체인지 몰라도 알아서 실행됨
```

다형성이 없으면 결제 수단이 늘 때마다 `if-else`를 계속 수정해야 하지만, 다형성을 쓰면 호출부 코드는 그대로 두고 새 클래스만 추가하면 됨 → **OCP(개방-폐쇄 원칙)**와 직결.

## 반복 오답 패턴 정리

이번 라운드에서 반복적으로 나타난 실수 유형 — 다음 복습 때 우선 점검할 것:

1. **원인과 결과가 뒤바뀜**: "타입 소거는 런타임에 타입을 알아서 지워진다"(X) → 실제로는 컴파일 타임엔 타입을 다 알고 있고, 하위 호환성 때문에 일부러 지움. "Stream이 최종연산이 있어서 지연된다"(X) → 성능(단일 순회, short-circuit) 때문에 지연되도록 설계됨.
2. **`==`/`.equals()` 방향 반전**: `==`가 값 비교, `.equals()`가 주소 비교라고 반대로 암기하고 있었음.
3. **"전역"이라는 표현 남용**: static을 "전역 변수"로 이해하는 C 계열 습관 — Java는 "클래스 레벨 소속"이 정확한 표현.
4. **속도 우위 오판**: TreeMap이 "제일 빠르다"고 잘못 판단 — 실제로는 정렬을 위해 O(log n)으로 HashMap(O(1))보다 느림.
